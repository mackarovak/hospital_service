## BUG-001 — Профиль принимает строку из пробелов как ФИО

**Статус:** New.
**Серьёзность:** Medium.
**Приоритет:** Medium.

**Предусловие:** Авторизован пациент `patient1`.

**Шаги:**

1. Отправить PATCH `/api/v1/patient/profile`.
2. Передать `first_name: "   "` и `last_name: "   "`.

**Тестовые данные:**

```json
{
  "first_name": "   ",
  "last_name": "   "
}
```

**Фактический результат:** HTTP 200. Пробелы сохранены в базе.

**Ожидаемый результат:** HTTP 400 с сообщением о пустых обязательных полях. Значения не сохраняются.

**Влияние:** Некорректное ФИО может попасть в медкарту и отчёты.

**Рекомендация:** Тримить строку и проверять, что поле содержит хотя бы один непробельный символ.

## BUG-002 — Врач может создать пересекающиеся окна приема

**Статус:** New.
**Серьёзность:** Medium.
**Приоритет:** High.

**Предусловие:** Авторизован врач `doctor1`.

**Шаги:**

1. Отправить POST `/api/v1/doctor/slots` со временем 10:00–11:00.
2. Повторно отправить POST `/api/v1/doctor/slots` со временем 10:30–11:30.

**Тестовые данные:**

```json
{"starts_at":"2027-12-01T10:00:00","ends_at":"2027-12-01T11:00:00"}
```

```json
{"starts_at":"2027-12-01T10:30:00","ends_at":"2027-12-01T11:30:00"}
```

**Фактический результат:** Оба запроса получили HTTP 201 и создали два пересекающихся слота.

**Ожидаемый результат:** Второе окно должно быть отклонено HTTP 409 или HTTP 400 с понятным сообщением о пересечении времени.

**Влияние:** Пациент может выбрать несколько взаимозависимых или дубль-слотов в одном временном диапазоне. Врач получает некорректное расписание и повышенный риск двойной записи.

**Рекомендация:** Перед созданием проверять существующие слоты врача по условию пересечения: новое начало меньше конца существующего и новое завершение больше начала существующего.

**Проверка после исправления:** Повторить сценарии с частичным пересечением, полностью вложенным интервалом и совпадающими границами.

## BUG-003 — Пациент может забронировать прошедшее окно напрямую через API

**Статус:** New.
**Серьёзность:** High.
**Приоритет:** High.

**Предусловие:** В базе существует свободное окно с датой начала в прошлом. Пациент авторизован как `patient1`.

**Шаги:**

1. Создать в базе свободный slot с началом в прошлом.
2. Получить его UUID.
3. Отправить POST `/api/v1/patient/slots/{slot_id}/book` от имени пациента.

**Тестовые данные:**

```text
slot_id: 107aae80-2bcc-4277-8827-136dbbf8bf30
starts_at: прошедшая дата
ends_at: прошедшая дата
patient: null
```

**Фактический результат:** Запрос получил HTTP 200. Прошедший слот был привязан к пациенту.

**Ожидаемый результат:** Запрос должен быть отклонён HTTP 409 или HTTP 400. Слот должен оставаться свободным.

**Влияние:** Можно создать запись на прошедшее время, показавшуюся пользователю или отправившуюся через прямой API-вызов вне обычного UI.

**Рекомендация:** При бронировании проверять, что `starts_at > timezone.now()` и что slot ещё свободен в одном атомарном UPDATE-запросе.

**Проверка после исправления:** Повторить бронирование прошедшего, свободного будущего и уже занятого slot; проверить, что ни одна прошедшая запись не создаётся.
