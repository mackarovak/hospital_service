# Шаг 4. Тест-кейсы

## TC-001. Вход пациента с корректными данными

Предусловие: аккаунт `patient1/password` создан seed.

| Шаг | Действие | Ожидаемый результат |
|---|---|---|
| 1 | Открыть `/login` | Открылась страница входа |
| 2 | Ввести `patient1` в поле логина | Значение принято |
| 3 | Ввести `password` в поле пароля | Значение принято |
| 4 | Нажать «Войти» | Получен JWT, сохранена роль PATIENT |
| 5 | Проверить редирект | Открылась `/patient` |

Приоритет: P0. Автоматизация: pytest/API и Vitest UI.

## TC-002. Вход с неверным паролем

Предусловие: пользователь существует.

| Шаг | Действие | Ожидаемый результат |
|---|---|---|
| 1 | Открыть `/login` | Форма доступна |
| 2 | Ввести корректный логин и неправильный пароль | Значения приняты |
| 3 | Нажать «Войти» | Появилось понятное сообщение об ошибке |
| 4 | Проверить редирект | Остались на `/login`, токен не сохранён |
| 5 | Проверить API | HTTP 401 |

Приоритет: P0. Автоматизация: pytest + Vitest.

## TC-003. Пациент не имеет доступа к разделу врача

Предусловие: выполнен вход как пациент.

| Шаг | Действие | Ожидаемый результат |
|---|---|---|
| 1 | Открыть `/doctor` вручную | Отображено 403 или выполнен безопасный redirect |
| 2 | Вызвать `/api/v1/doctor/patients` | HTTP 403 |
| 3 | Вызвать `/api/v1/doctor/check` | HTTP 403 |

Приоритет: P0. Автоматизация: pytest.

## TC-004. Пациент просматривает только свою медкарту

Предусловие: пациент и врач связаны seed.

| Шаг | Действие | Ожидаемый результат |
|---|---|---|
| 1 | Войти как пациент | Доступен кабинет пациента |
| 2 | Открыть медкарту | Отображается карта пациента |
| 3 | Изменить ID запроса на чужого пациента | HTTP 403 или корректная ошибка |

Приоритет: P0. Автоматизация: API pytest.

## TC-005. Валидация пустого имени профиля

Предусловие: patient1 авторизован.

| Шаг | Действие | Ожидаемый результат |
|---|---|---|
| 1 | Открыть `/patient/profile` | Форма загружена |
| 2 | Указать пробелы в `first_name` | Поле содержит пробелы |
| 3 | Нажать «Сохранить» | HTTP 400, поле подсвечено, пробелы не сохранены |

Приоритет: P1. Связанный дефект: DEF-001.

## TC-006. Создание пересекающихся слотов

Предусловие: выполнен вход врачом `doctor1`.

| Шаг | Действие | Ожидаемый результат |
|---|---|---|
| 1 | Создать слот 10:00–11:00 | HTTP 201 |
| 2 | Создать слот 10:30–11:30 | HTTP 400 или HTTP 409 |
| 3 | Проверить количество слотов врача | Второй слот не сохранён |

Приоритет: P1. Связанный дефект: DEF-002.

## TC-007. Бронирование прошедшего слота

Предусловие: в базе есть свободный прошедший slot и авторизован пациент `patient1`.

| Шаг | Действие | Ожидаемый результат |
|---|---|---|
| 1 | Отправить POST на `/api/v1/patient/slots/{id}/book` | HTTP 400 или HTTP 409 |
| 2 | Проверить поле patient слота | Слот остаётся свободным |
| 3 | Повторить для будущего свободного slot | HTTP 200 и связь с пациентом |

Приоритет: P0/P1. Связанный дефект: DEF-003.

## TC-008. Запись пациента на свободный слот

Предусловие: для врача есть свободный слот.

| Шаг | Действие | Ожидаемый результат |
|---|---|---|
| 1 | Войти как пациент | Доступен кабинет |
| 2 | Выбрать специальность и врача | Отобразились доступные врачи |
| 3 | Выбрать свободный слот | Слот отмечен выбранным |
| 4 | Подтвердить запись | Слот стал занятый, запись появилась в appointments |
| 5 | Повторно открыть слот | Повторной записи нет |

Приоритет: P0/P1. Автоматизация: workflow k6/API.

## TC-009. Повторное бронирование одного слота

Предусловие: slot уже забронирован одним пациентом.

| Шаг | Действие | Ожидаемый результат |
|---|---|---|
| 1 | Отправить POST на `book_slot` вторым пациентом | HTTP 409 |
| 2 | Повторить запрос тем же пациентом | Слот не создаёт двойную запись |

Приоритет: P0/P1. Метод: state transition/concurrency.
