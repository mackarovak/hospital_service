# Шаг 3. Стратегия тестирования и анализ рисков

## Цель

Проверить соответствие MedCat её назначению: регистрация и аутентификация пользователей, разграничение ролей пациента и врача, ведение профиля и медкарты, запись на приём, управление слотами и устойчивость приложения.

## Уровни тестирования

| Уровень | Объект | Инструменты | Критерий окончания |
|---|---|---|---|
| Unit | Сервисы, валидация, модели, React-компоненты | pytest, Vitest | Все unit-тесты зелёные |
| Integration | Django ORM, auth, взаимодействие frontend/backend | pytest-django | Основные сценарии БД и API проходят |
| API | REST-контракты, роли, коды ответов | pytest + HTTPX/Django Client | Позитивные и негативные сценарии проходят |
| UI | Реальные пользовательские сценарии в браузере | Vitest и ручной Chromium | Критические сценарии пациентов и врача проходят |
| System | Полная работа Docker Compose, seed и наблюдаемость | Docker Compose, curl | Система запускается и основные сценарии доступны |
| Load | Устойчивость и latency под нагрузкой | k6 | Нет критических превышений порогов |

## Виды тестирования

### Функциональное

- вход и выход;
- регистрация пациента и врача;
- просмотр профиля и медкарты;
- редактирование профиля;
- triage и подбор специалиста;
- запись на приём;
- отмена приёма;
- создание и удаление слота;
- просмотр истории записей;
- управление медицинскими записями.

### Нефункциональное

- Производительность и нагрузка;
- usability и адаптивность;
- совместимость браузеров;
- безопасность доступа;
- отказоустойчивость;
- наблюдаемость через logs, metrics и health-check;
- резервируемость и целостность данных.

### Безопасность

- авторизация и аутентификация;
- проверка роли на backend и frontend;
- обработка истёкшего или подделанного JWT;
- защита от доступа к чужой медкарте;
- защита от XSS в текстовых полях;
- проверка SQL-инъекций как негативного ввода;
- защита от массового создания записей и race-condition.

### Совместимость

- Chromium Desktop;
- мобильный viewport;
- адаптивные страницы;
- браузерная локализация RU;
- разная ширина экрана и масштабирование.

## Методы тестирования

- Эквивалентное разбиение;
- анализ граничных значений;
- таблицы решений;
- pairwise-подход для комбинаций ролей и API-действий;
- state transition для записи на приём;
- cause-effect для triage;
- exploratory testing;
- тестирование по сценариям;
- повторная проверка после исправления дефектов;
- monkey testing для случайных некорректных входов;
- нагрузочное тестирование ступенчатое и stress.

## Приоритизация

| Приоритет | Функциональность |
|---|---|
| P0 | Login/logout, разграничение ролей, просмотр/изменение медкарты, защита чужих данных |
| P1 | Регистрация, профиль, запись и отмена приёма, слоты врача, триаж |
| P2 | Поиск пациентов, пагинация, печать медкарты, фильтрация расписания |
| P3 | UI-полировка, подсказки, нечастые сочетания viewport и браузеров |

## Анализ рисков

| ID | Риск | Вероятность | Влияние | Контрмеры |
|---|---|---|---|---|
| R-01 | Пациент получает доступ к чужой медкарте | Средняя | Критическое | API/role-тесты, UI-переходы, автоматическая проверка межролевого доступа |
| R-02 | Два пациента одновременно бронируют один слот | Средняя | Высокое | Тест 409, атомарный UPDATE, проверка повторного запроса |
| R-03 | Несанкционированное изменение medcard записи | Средняя | Критическое | Проверки владельца пациента и врача, отрицательные API-тесты |
| R-04 | Некорректные данные сохраняются в базе | Высокая | Высокое | Граничные значения, enum-проверки, белый список полей |
| R-05 | Пересекающиеся слоты создаются в расписании врача | Подтверждённая | Высокое | Проверка пересечения интервалов до создания slot |
| R-06 | Неверный подбор специальности в triage | Средняя | Высокое | Таблица ключевых симптомов и edge-case сценарии |
| R-07 | Нагрузочное падение при росте VUs | Средняя | Высокое | k6 smoke/read/workflow/stress, thresholds, Grafana |
| R-08 | JWT истекает или подделывается | Низкая | Критическое | Негативные токены и истечение времени |
| R-09 | Ошибки разных окружений Docker/Kubernetes | Средняя | Высокое | Health-check, CORS, переменные окружения и миграции |
| R-10 | Потеря данных или некорректная миграция БД | Низкая | Критическое | Backup/check, повторный seed и миграции |
| R-11 | Разрыв frontend и backend контрактов | Средняя | Высокое | API contract checks и Vitest |
| R-12 | UI ломается на мобильной ширине | Средняя | Среднее | Chromium viewport 390x844, горизонтальный scroll-check |
| R-13 | Прошедший slot бронируется через прямой API-вызов | Подтверждённая | Высокое | Проверять starts_at и атомарно закрывать slot при бронировании |

## Критерии входа

- Приложение собрано и запущено через Docker Compose;
- backend отвечает health-check;
- seed создал пользователей и демо-связи;
- frontend доступен;
- тестовая база чистая;
- тестовые инструменты установлены.

## Критерии выхода

- Все P0-тесты прошли;
- Нет незакрытых Critical/High дефектов;
- Backend pytest прошёл;
- Frontend Vitest прошёл;
- Browser E2E прошёл;
- k6 smoke прошёл базовые thresholds;
- Все отклонения задокументированы.
