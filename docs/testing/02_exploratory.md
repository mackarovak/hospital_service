# Шаг 2. Исследовательское тестирование

## Методика

Для первого прогоня использованы:

- ручные HTTP-запросы к реальному backend через Docker Compose;
- проверка позитивных и негативных сценариев авторизации;
- проверка разграничения ролей;
- проверка границ и некорректных значений профиля;
- проверка создания слотов врача;
- анализ UI-кода для поиска уязвимых границ ввода.

Среда: Docker Compose, PostgreSQL, Django REST Framework, локальный frontend на `http://localhost`.

## Подтверждённые сценарии без дефекта

| Сценарий | Результат |
|---|---|
| Health-check backend | HTTP 200, `{"status":"ok"}` |
| Неправильный пароль | HTTP 401 |
| Неизвестный логин | HTTP 401 |
| Пациент запрашивает doctor endpoint | HTTP 403 |
| Врач запрашивает patient endpoint | HTTP 403 |
| Пустой triage | HTTP 400 |
| Неправильное время при создании слота | HTTP 400 |
| Начало слота позже конца | HTTP 400 |
| Имя длиной 100 символов | HTTP 200 |
| Имя длиной 101 символ | HTTP 400 |
| Телефон длиной 31 символ | HTTP 400 |
| Будущая дата рождения | HTTP 400 |
| Некорректная дата рождения | HTTP 400 |

## Найденные дефекты

### DEF-001. Профиль принимает пустые значения из одних пробелов

Серьёзность: Medium.
Приоритет: Medium.

Шаги:

1. Авторизоваться как `patient1`.
2. Отправить `PATCH /api/v1/patient/profile`.
3. Передать `first_name = "   "` и `last_name = "   "`.

Фактический результат: HTTP 200, пробелы сохранены в профиле.

Ожидаемый результат: HTTP 400 с ошибкой валидации для обязательных полей.

Окружение: Docker Compose, PostgreSQL.

### DEF-002. Врач может создать пересекающиеся окна приёма

Серьёзность: Medium.
Приоритет: High.

Шаги:

1. Авторизоваться как `doctor1`.
2. Создать слот 10:00–11:00.
3. Создать второй слот 10:30–11:30.

Фактический результат: оба запроса получили HTTP 201 и создали пересекающиеся слоты.

Ожидаемый результат: второй слот отклоняется HTTP 400 или HTTP 409.

### DEF-003. Пациент может забронировать прошедшее окно

Серьёзность: High.
Приоритет: High.

Шаги:

1. Создать свободное окно с началом в прошлом.
2. Авторизоваться как `patient1`.
3. Отправить POST `/api/v1/patient/slots/{slot_id}/book`.

Фактический результат: HTTP 200, прошедший слот привязан к пациенту.

Ожидаемый результат: прошедший слот не может быть забронирован; ответ 400 или 409.

Примечание: после проверки тестовые слоты удалены, демо-профиль и seed-восстановлены.
